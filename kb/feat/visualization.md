# Tree ordering and visualization outputs

TreeKnit does not draw anything itself. It orders the output trees so that a tanglegram of a pair has few crossing lines, writes auspice JSON files with MCC colorings, and writes the ARG in a format that IcyTree reads [[doc](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/docs/src/visualization.md?plain=1#L1-L17)].

## Ordering of the output trees

In the last round of the pipeline, for each pair `(i, j)` in order, TreeKnit ladderizes tree 1 when `i == 1` and then calls `sort_polytomies!(trees[i], trees[j], MCCs; strict)` [[src](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/src/main.jl#L61-L70)]. With more than two trees, a tree is sorted once for each pair it belongs to, so the last such pair decides its final order.

- **Ladderize** (TreeTools `ladderize!`): at every internal node, sort the children by the number of leaves below them, **smallest first**, then by label in string order [[src](https://github.com/PierreBarrat/TreeTools.jl/blob/2fb33ac3a5891a9cf0d25c76d2bc0270e571a6b8/src/methods.jl#L837-L859)]. The TreeTools docstring says the opposite ("largest clades left")
- **Non-strict sort** (`strict = false`) [[src](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/src/mcc_tools.jl#L176-L263)]: tree 1 is the guide and does not change. For each MCC, record the order of its leaves in tree 1. Assign every node of tree 2 to an MCC with `map_mccs`. At each node of tree 2, children in the same MCC as the node go in the order of their first leaf in tree 1. Other children are ordered by clade size, smallest first
- **Strict sort** (`strict = true`): strictly resolved trees can keep polytomies that mix MCCs, and the non-strict rule can then give crossing lines. The strict sort resolves copies of both trees liberally, ladderizes the copy of tree 1, sorts the copy of tree 2 with the non-strict rule, and then reorders the children of **both** real trees by the smallest leaf position of the copies. Tree 1 can therefore change order
- **Result**: in a tanglegram of the pair, leaves of the same MCC appear in the same order in both trees. The NY data test checks this for strict resolution [[src](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/test/NYdata/test.jl#L68-L73)]

## Auspice JSON

With `--auspice-view`, or with `write_auspice_json(dir, trees, MCCs::MCC_set)`, TreeKnit writes one file `auspice_<tree label>.json` per tree into `dir`, which must end with `/` [[src](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/src/mcc_IO.jl#L90-L152)]. The files follow the auspice dataset format version 2 with only the fields that auspice needs to draw a tree. [`formats.md`](formats.md) gives the structure.

- **One coloring per other tree**: the key and the title are `mcc_<a>_<b>`, where `a` and `b` are the two tree labels in alphabetical order, with the type `ordinal`. With `K` trees, each file has `K - 1` colorings. Auspice builds an ordinal scale only from integer values, so the string values give a categorical scale [[src](https://github.com/nextstrain/auspice/blob/37bf9ce1e3b9a8cbdf1ebfd77bd8d7bdb6dfdc2d/src/util/colorScale.ts#L210-L257)]
- **Node values**: each node gets the 1-based index of its MCC in the pair's MCC list, as a string. Internal nodes get an MCC through the Fitch mapping of `map_mccs`. A node that belongs to no MCC gets the string `"null"`, which auspice shows as one more category, not as missing data [[src](https://github.com/nextstrain/auspice/blob/37bf9ce1e3b9a8cbdf1ebfd77bd8d7bdb6dfdc2d/src/util/globals.js#L173-L194)]
- **Divergence**: `div` is the sum of branch lengths from the root. A `missing` branch length counts as 0 and is set to `0.0` in the tree itself
- **Tanglegram**: the documentation tells users to drop two files together on <https://auspice.us> and to choose the MCC coloring in the "color by" menu [[doc](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/docs/src/visualization.md?plain=1#L8-L17)]. auspice.us loads the first two dropped files as the left and right trees, in drop order, whatever their names [[src](https://github.com/nextstrain/auspice.us/blob/f8beac16f71ea0f38e81f7a1449e3e26b287dfcb/auspice_client_customisation/handleDroppedFiles.js#L160-L171)], and joins tips with the same name
- **Documented signature**: the documentation gives `write_auspice_json(filepath, tree1, tree2, MCCs::Vector{Vector{String}})`. No such method exists; the only method takes a vector of trees and an `MCC_set`
- **Schema conformance**: `meta.updated` is the empty string, which does not match the date pattern that the augur export schema requires for this field. Auspice still displays the files (see [`treeknit-ecosystem.md`](../reports/treeknit-ecosystem.md))

## ARG viewers

- **IcyTree**: the documentation recommends dropping the extended Newick file of the ARG into IcyTree [[doc](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/docs/src/visualization.md?plain=1#L3-L4)]. IcyTree joins the copies of a hybrid node by their `#H<i>` id, and it can color nodes by the `segments` annotation
- **TreeKnit-web**: the documentation names a separate prototype viewer, `neherlab/TreeKnit-web`, that draws ARGs with segment colors [[doc](https://github.com/PierreBarrat/TreeKnit.jl/blob/dbbc89ac691fed0949a622eedbae103787b89320/docs/src/visualization.md?plain=1#L6)]. It is a prototype from 2022 that joins hybrid copies by equal label text, not by the `#H` id, at <https://treeknit-web.vercel.app>
